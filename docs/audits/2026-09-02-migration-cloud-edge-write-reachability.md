# What a Migration Cloud import writes onto a box, and what can never leave it

**Date:** 2026-09-02
**Scope:** `apps/migration_cloud/landers/**`, `apps/migration_cloud/orchestrator.py`, the edge sync rail (`apps/api/sync_services.py`, `apps/sync_engine/rail_coverage.py`).
**Every figure below is reproducible by a committed command.** They are listed in [§7](#7-how-to-reproduce-every-number-here).

---

## 1. The finding, in one paragraph

An edge appliance can be given a school's entire history through Migration Cloud, and **23 of the 35 tenant models those imports write are on no sync rail at all**. A model that is not registered on the rail does not fail to sync: it produces **no error, no conflict and no refusal**. The rows land, the bundle reports `APPLIED`, the progress board turns green, and the data stays on that box forever with nothing anywhere saying so. **21 of the 33 canonical domains a school can import put NOTHING on the cloud** except the importer's own bookkeeping — among them health records, the library catalogue, bus routes and rosters, hostel rooms and placements, meal balances, discipline incidents, every message sent, transcripts, athletics, payroll, the timetable, and **every guardian account an import creates**.

None of that is necessarily wrong. A school with no reliable uplink genuinely may want its library on the appliance. What was wrong is that **nobody was choosing it** — the decision was made by which lander happened to run, and would surface only when the box died.

## 2. Correcting the brief

The task was framed with numbers from a crude AST scan. The code disagrees with several of them, and the code wins.

| Claim in the brief | What the code says | Why |
|---|---|---|
| "21 distinct models written, 14 not on the rail" | **38 distinct models written**, 26 not on the rail (23 school data + 3 import bookkeeping) | The scan looked for `Model.objects.create\|get_or_create\|update_or_create\|bulk_create`. The dominant idiom in this package is `upsert_with_conflict_detection(ctx=ctx, domain=..., model=Route, ...)`, where the model name never appears beside a write call. Every first-class lander shipped since v3.26 writes that way. |
| "`DynamicFieldValue` (7 sites), `DynamicFieldDefinition` (4)" | **All 33 domains write both** | Not through the landers. `orchestrator._ResidualCapture` runs behind *every* lander that leaves `sweeps_custom_columns` False — which is all of them — and persists every unmapped source column to `DynamicFieldValue` under `migration_residual:<domain>`. "No source column is ever dropped" and "every domain writes something that cannot sync" are the same sentence read from two ends. |
| "`TeacherProfile` is registered but in `_INSERT_HELD_ENTITIES`" | **Confirmed.** `staff` and `structure` both write it, and it is reported as *refused on create*, never as reaching the cloud | Registered ≠ insertable. A lander-created teacher on a box can never be created on the cloud. |
| "17 entities on the rail, ~370 tenant-scoped models, ~353 not on the rail" | **Confirmed exactly**: 17 / 370 / 353 | `python manage.py edge_rail_coverage` |
| "The scan is a LOWER BOUND" | Confirmed, and the gap is not small | 21 → 38 models. For `transport`, `library`, `hostel`, `health`, `cafeteria`, `events`, `communications` and the three athletics landers, the pattern scan resolves *nothing at all*. |

One further correction, which changes what the guard is allowed to claim: `migration_cloud.MigrationIdMapping`, `MigrationConflict` and `MigrationBundle` **do** carry a `school` FK, so they are tenant-scoped by the same definition `edge_rail_coverage` uses, and they are stranded too. They are the importer's own bookkeeping and are regenerated by the next import, so they are reported in **a separate column** rather than dropped. Dropping them would have been the guard quietly making the judgement the operator is supposed to make.

## 3. How the measurement was done

`scripts/audit_lander_write_reachability.py` resolves what the landers write by inter-procedural AST analysis over `apps/migration_cloud/landers/*.py` plus `apps/migration_cloud/orchestrator.py`. Five things have to work together, because the landers use all five:

1. **Model-name binding** — `from apps.X.models import Y` resolved through the **live app registry** (so a re-exported model lands on its real label), `apps.get_model("x","Y")`, `get_user_model()`, aliasing. Module scope *and* function scope: landers import the shared upsert inside `land()` as often as at module scope, and treating a local import as absent made `attendance_lander` resolve to "writes nothing" while writing every attendance row a school has.
2. **Direct writes** — manager and queryset-tail mutations, and `<instance>.save()`.
3. **Writes through a helper's parameter** — every function gets a summary of the models it writes outright *plus the parameters it writes through*. `upsert_with_conflict_detection` summarises as "writes whatever arrives as `model`"; `save_scoped` as "writes whatever arrives as `obj`". Call sites bind those parameters and the whole thing runs to a fixed point. **This is what finds `Route`.**
4. **Models carried through a tuple** — `structure_lander` hands seven model classes to `_provision_row` as one `models=(AcademicYear, Term, ...)` argument and destructures them inside. Without per-element binding, the single most rail-relevant lander in the package resolves to "writes nothing it can name".
5. **Return types** — `student = resolve_student(student_model=StudentProfile)` then `save_scoped(student, ...)`; `obj, _, _ = upsert_with_conflict_detection(model=TeacherProfile, ...)` then `_sweep_custom_attributes(obj, ...)`. Summaries record what a function returns, concretely or as "whatever arrived as parameter P", and modules are analysed twice so the second pass has that oracle.

**Unresolved write sites: 0.** Every write site in the package resolves to a named model. Any that did not would be counted and the affected domain reported as a **FLOOR**, never as a complete answer — the discipline `edge_rail_coverage --counts` already uses for tables it cannot read.

### Proving the detector before believing it

A scan that has never been shown reporting a non-zero answer is indistinguishable from a broken scan. `--self-test` plants two synthetic landers inside the real package — one exercising all seven supported idioms, one that writes nothing — runs the real resolver over them, and asserts the first is fully reported with zero unresolved sites and the second reports nothing of its own. It removes them in a `finally`. It is asserted by a test, not just available as a flag.

The rail side is asked of `sync_services._sync_conflict_policy` and `_get_entity_config` (via `apps/sync_engine/rail_coverage.py`), **not** `policy_registry.get_policy` — the registry misses the `_LWW_SAFE_ENTITIES` tier and answers wrongly for 13 of the 17 entities.

### The three that should change a plan

1. **`guardians` puts nothing on the cloud.** It writes `accounts.User` *and* `people.StudentGuardian`, and both are on no rail. A parent account minted by an import on a box exists only on that box: the parent cannot sign in anywhere else, and the cloud has no record that the relationship exists. `staff` and `structure` write `accounts.User` too. **Identity created by an import on an appliance is appliance-local.**
2. **`behavior` → `academics.Incident` is stranded.** Safeguarding and discipline records are exactly the category a school is least able to lose and most likely to be asked to produce.
3. **`schedule`, `payroll`, `compliance` and `reports` write only `DynamicFieldValue`.** Their landers have no first-class model to land into (documented honestly in each lander), so the whole domain is DFV — which is stranded. Those four domains are 100% box-resident by construction, on every deployment.

`metadata.DynamicFieldValue` / `DynamicFieldDefinition` appear under all 33 domains. That is the residual-capture net, not an oversight in the table, and it is why **no domain is clean**: even `academic_sessions`, whose two first-class models both ride the rail, still strands whatever source columns did not map.

## 5. The guard

### Where it is, and why it cannot be bypassed

The load-bearing guard is **`apps/migration_cloud/edge_reachability.guard_before_apply`, called from `orchestrator._apply_bundle_inner` after the jobs are built and before the dependency waves run** — after the last read, before the first write.

That location was chosen by mapping every path that can write tenant rows. Putting the check on the Apply button would have covered one of these:

| Entry path | Reaches the guard |
|---|---|
| Tenant connector wizard — `TenantMigrationApplyView` → `enqueue_apply` → outbox drain | yes |
| Customer self-serve — `MigrationIntakePromotionApproveView` → `begin_promotion` → `enqueue_apply` | yes |
| DRF — `POST /…/api/v1/bundles/<pk>/apply/` → `MigrationCloudApplyView` | yes |
| Celery task `migration_cloud.apply_bundle` (dispatchable by task-name string) | yes |
| `HeavyWorkOutbox` kinds `mc_apply_bundle` **and** `mc_advance_bundle` with `apply_after` | yes |
| `repair.repair_bundle` (both the queued and the synchronous branch) | yes |
| `connector_bundle_bridge.run_bundle_pipeline` (connector import, transfer intake) | yes |
| Student-transfer FSM (`people.continue_applying_transfers` beat, every 60s) | yes |
| Self-healing autopilot `workflow_fix_handlers` → `enqueue_apply` (unattended) | yes |
| `manage.py mc_recover_import --repair` / `--sync` | yes |
| In-process daemon thread from `kick_heavy_work_drain(force_local=True)` | yes |

All of them converge on `apply_bundle` → `_apply_bundle_inner`. The wizard, incidentally, does **not** dispatch the apply through the dotted-string writer registry — `apps/setup_studio/wizards/legacy_data_extraction_pipeline.json` resolves `write_migration_seeding` via `wizard_engine._import_dotted`, and that writer stops at `MAPPED` (it calls `enqueue_advance` with no `apply_after`). The apply comes from the tenant connector wizard's own view. The dotted-string dispatch was checked because it is invisible to grep; it is not a bypass here.

**One seam does not pass through `apply_bundle`, and it is named rather than hidden:** `quarantine_resolution.replay_operator_edits` and `auto_remediate._attempt_land_quarantine_row` call `orchestrator._run_lander_under_schema` directly to land individual held rows. Those are follow-ups to an import that has already been assessed and warned about — the same bundle, the same domains — so they are not a way to import a fresh domain unseen. They are listed in §8 as the remaining work.

### What the operator actually sees

1. **On the Review & Import page, beside the button** — `templates/migration_cloud/connector/bundle_review.html` renders `live_import.edge_stranding` (from `live_import_attention.compose_live_import` → `edge_reachability.review_notice`) directly above the *Import into my school* form. It names each domain and the row count that will stay, before anything is pressed.
2. **In the live event stream** — a `kind="warning"` progress event carrying the same sentence, so the warning is in the import's own timeline and not only in a log.
3. **Durably on the bundle** — `mapping_summary["edge_stranded_writes"]`, so an audit months later can see what the operator was told.
4. **In preflight** — `preflight.check_edge_reachability`, included in `run_all`.
5. **In a shell, which is how a box is actually operated** — `manage.py edge_import_reachability --bundle <id>` prints the same assessment from the same resolver, so the terminal and the page cannot disagree.
6. **In the logs** — a `logger.warning`, last and least, because a log line is not a warning an operator sees.

### It does not block by default

The policy resolves through the configurability cascade — `apps/migration_cloud/defaults.py` key `migration_cloud.edge.stranded_write_policy`, i.e. env `MIGRATION_CLOUD__MIGRATION_CLOUD__EDGE__STRANDED_WRITE_POLICY` → `RuntimeDefaults` → seed. No literal decides it.

| Policy | Behaviour |
|---|---|
| `warn` (**default**) | Assess, record, show it on the page, emit the event, apply anyway. |
| `refuse` | Stop an import whose stranding nobody has acknowledged: bundle `FAILED`, zero landers run, reason recorded. |
| `off` | Do not assess. For a deployment that is knowingly and permanently the only copy. |

**Making the choice explicit** is `manage.py edge_import_reachability --bundle <id> --accept <domain> --actor <who>`, which records the decision, the domains, the time and the actor on the bundle (`edge_reachability.acknowledge` is the same thing from Python). Acknowledgement is **per domain and per bundle** — accepting `library` does not accept `health`, and `StrandedWriteReport.acknowledged` is True only when *every* stranding domain has been ruled on. A partial acknowledgement is not an acknowledgement, because a domain nobody has ruled on is exactly the case this exists to surface. Accepting a domain the bundle does **not** strand is refused rather than recorded: an acknowledgement about data that is not in the import reads later as a decision somebody made about it, and it silences nothing.

### Honesty rules it obeys

* **Two failures, two figures, and they add up.** A `students` artifact lands `people.StudentProfile`, which rides the rail: the ROWS reach the cloud and only the unmapped source COLUMNS stay behind. A `library` artifact lands `schoolops.LibraryItem`, which rides nothing: the rows themselves never leave. Reporting both as "N rows will stay on this box" would tell a school its entire student roster was lost because one spreadsheet column did not map — and the next real warning would be ignored. `rows_stranded` counts only the first kind; the partial kind is reported separately and named as such. A third line names the `insert_held` case (`staff`, `structure` → `people.TeacherProfile`), where the rail carries the model and still refuses to create it.
* **Row counts can be a floor.** `MigrationArtifact.row_count` is null for formats the profiler cannot count rows in. Those artifacts are counted separately and the message reads *"at least N rows (1 file could not be row-counted)"* — with the plural right, because "1 files" in a warning about data loss reads as a machine nobody proof-read, which is exactly when a person stops believing the number beside it.
* **An unreadable rail reports nothing, not zero.** If the rail registry cannot be resolved on a deployment, the report carries `rail_unavailable` and **no figures at all** — because "0 stranded" and "I could not look" are the same shape and opposite meanings.
* **An unregistered domain is the worst case, not the empty one.** A canonical domain with no lander falls through to the `custom_fields` catch-all, which writes the whole row to `DynamicFieldValue`. `write_targets_for()` returns the catch-all's targets rather than `()`, so a brand-new domain never reports as costing nothing to import.
* **It is inert on the cloud.** Scoped to a sovereign box via `sync_engine.edge_enabled`; a multi-tenant deployment pays and sees nothing.

## 6. Keeping the table honest

`apps/migration_cloud/landers/write_targets.py` is a **measured** table, not a hand-written one: it is generated by the resolver. Two things stop it rotting:

* `python scripts/audit_lander_write_reachability.py --check-declaration` — exits non-zero on any difference in either direction (a lander that gains a model, or a declared model no longer written).
* `apps/migration_cloud/tests/test_edge_write_reachability_2026_09_02.py::DeclarationIsMeasuredTests` runs that comparison **and** the resolver's `--self-test`, so both the declaration and the detector's ability to find anything are asserted in CI.

Proven capable of failing, by hand and by harness:

* By hand — deleting `"schoolops.Route"` from the `transport` entry makes `--check-declaration` exit 1 with `transport: resolver found undeclared writes ['schoolops.Route']`; restoring it returns 0.
* By harness — the gate is registered in `scripts/verify_gates_can_fail.py` as `lander-write-targets`, which plants that same deletion in a detached worktree at `HEAD` and asserts the gate wakes up. `python scripts/verify_gates_can_fail.py --gate lander-write-targets` → **PROVEN** (102s). That registration is not optional: `pre_push_boundary_check.py`'s `gates-can-fail-coverage` step refuses a new `DJANGO_GATES` entry that carries neither a mutation nor a written exemption.

## 8. What this does not close

* **`_run_lander_under_schema` has two callers outside `apply_bundle`** — `quarantine_resolution.replay_operator_edits` and `auto_remediate._attempt_land_quarantine_row`. They land held rows for a bundle that has already been assessed, so they cannot introduce an unseen domain, but they do not re-state the warning.
* **The guard reports; it does not shrink the gap.** Twenty-three stranded school-data models is an argument for registering entities on the rail (`schoolops.Route`, `schoolops.LibraryItem`, `academics.Incident` and `people.StudentGuardian` are the obvious first four), not for warning about them forever. `apps/sync_engine/rail_coverage.py` is where each absence must be argued or closed.
* **`metadata.DynamicFieldValue` is the single highest-value registration on the list.** It is written by all 33 domains and it is where every unmapped source column in the product ends up. Nothing else would move so many rows onto the rail at once.
* **Acknowledgement has no browser control yet.** It is makeable from a shell (`manage.py edge_import_reachability --accept`), and the Review & Import page shows the *Accepted* badge for a domain already accepted, but there is no button. Under the default `warn` policy nothing is blocked, so this is a gap in ergonomics rather than in safety.
