What the Assigner Cannot See Today

The assignment UI can save the mapping, but it does not let the operator inspect the role home, widgets, hidden sections, KPI order, mobile behavior, empty states, or permissions before assigning.
No side-by-side preview.
There is no inline visual proof of what Teacher vs Parent vs Student will see.
No impact summary.
The underlying pack schema can change modules, KPIs, theme, focus chips, and hidden cockpit sections, but the page does not summarize those changes.
No before/after confirmation.
A high-impact assignment can be made from two selects and one button without a preview gate.
Preview exists elsewhere.
Launch Studio has role previews; pack/blueprint previews are read-only. The missing work is integration into this assignment moment.

Recommended One-by-One Approval Order

This avoids mixing too many preview systems at once.

1. Dashboards by role
Highest relevance to your question; clear existing gap; strong underlying data already exists.
2. Feature/permission/sidebar impact preview
These decide what roles can see and do; they should share the same role/device preview shell.
3. Workflow activation preview
Dry-run engine exists; add a human-readable simulation before activation.
4. Forms/admissions preview
High user-facing risk; needs mobile/parent/applicant sample rendering.
5. Billing and communication previews
High trust impact, but should reuse the preview shell after it is proven.

Implementation Contract For Approval

No platform-wide code change should begin until the first design is approved. The first implementation should be the dashboards-by-role preview sidecar only.
Use existing architecture.
Reuse role_home_engine, dashboard_pack_resolver, get_preview_url, Launch Studio role preview entries, and pack preview patterns.
Keep it tenant-safe.
Only same-tenant preview URLs, no cross-tenant data, sample mode as default, live mode only when permissioned.
Make preview evidence auditable.
Store preview confirmation metadata before assignment where governance requires it.
Validate with tests.
Add template tests for sidecar markers, resolver tests for allowed packs, and browser/a11y checks after implementation.
