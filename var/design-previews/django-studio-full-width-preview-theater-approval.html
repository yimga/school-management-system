Revised approval direction

Replace cramped inline preview with a full-width preview theater

The inline preview in the screenshot is not fixable by making it a little wider. It is the wrong interaction pattern. The exceptional version uses the whole available canvas: configuration is compact, preview is large, proof is visible, and drawer/popout/new-tab options handle every case where inline rendering would be cramped.

Full-width first Studio-safe Preview theater No cramped iframe

What this changes

Inline preview becomes a small confidence snapshot only. The real preview opens in a full-width theater by default, with drawer and popout as power tools.

All applicable tenant and platform pages should use this rule: the most important work surface gets the width, rails collapse when they would squeeze the work.

Why the current pattern fails

Inline preview is trying to be too many things

  • The preview is a tall, narrow phone-like strip even when the user needs to verify a desktop dashboard.
  • Controls and preview share the same cramped vertical lane, creating leaking labels and unreadable text.
  • The page leaves large empty space unused while the important work is squeezed in the center.
  • There is no clear escalation from quick preview to real preview, popout comparison, or new-tab verification.

Platform-wide and tenant-wide rule

Every applicable page gets an intelligent full-width surface

The implementation must audit all pages and choose the right surface pattern instead of forcing every page into the same narrow card stack.

Applies after approval

Studio work modes

Overview, Experience, Automation, Outputs, Launch, and Control use the same workbench contract. Preview-heavy modes use theater/drawer/popout.

Django admin

Change forms and changelists use full-width field matrices, safe wrapping, clean rails, and save docks that never obscure active fields.

Configuration pages

Feature Controls, Theme, Report Card Builder, dashboards by role, forms, admissions, communications, and launch previews use dedicated builder surfaces.

Preview surfaces

Inline previews become confidence snapshots only. Real previews use theater, drawer, popout, or new-tab paths.

Tenant/operator separation

Tenant pages remain tenant scoped. Operator pages remain operator scoped. Wrong-plane links are critical defects.

Automation failure path

Automation gets native panels first. Legacy iframe failures show recovery, diagnostics, retry, and full-window open.

Audit proof loop

No implementation without page-by-page proof

After approval, the implementation must scan routes/templates, render representative pages, capture screenshots, fix gaps, and rerun until clean.
